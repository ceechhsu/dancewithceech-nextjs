# Private attendance backend

Attendance stays disabled until `ATTENDANCE_ENABLED=true`. Apply the reviewed `20260912163507_attendance_private.sql` migration before enabling it. This implementation has not applied any live migration or changed live configuration.

Required server configuration: `SUPABASE_URL` (or existing `NEXT_PUBLIC_SUPABASE_URL`), `SUPABASE_SERVICE_ROLE_KEY`, and `ATTENDANCE_INSTRUCTOR_EMAILS` as a comma-separated explicit allowlist. There is no automatic instructor bootstrap. Service credentials must never have a public environment prefix.

Existing Google login remains available to everyone. Attendance requires a fresh Google-authenticated session containing the provider subject and verified email. Sessions created before these claims were added must sign out and back in. Enrollment matching trims and lowercases the trusted Google email and binds its Google subject. A different subject cannot inherit a bound enrollment. Instructor email corrections reset that binding; current enrollment email authorizes historical access while snapshot names/emails remain immutable historical facts. Check-in rechecks current active enrollment, so roster email corrections take effect immediately. Missing enrollment emails remain usable for instructor marking only. Class dates, roster effective dates and meeting dates use the class timezone; effective_to is inclusive. Dropped students retain their own historical attendance access.

All private tables deny browser-role access through both privileges and RLS. Only the server service role may invoke `attendance_api`. API routes require a verified session and verify mutation origins. The RPC receives the server-calculated instructor flag, never a browser-provided role. It serializes operations and row locks meetings so finalization, token rotation, check-in and corrections cannot overwrite each other.

Check-in opens for ten minutes. Extension adds five minutes once. End finalizes missing roster records absent; cancellation excludes the meeting from student history. QR tokens are random, rotate in one-minute slots and accept only the current slot at the final database mutation check. Every token request requires a fresh instructor location and refreshes the meeting center. The instructor location sample remains valid for the one-minute QR slot; student samples must be no older than 30 seconds and both devices must report accuracy at most 50 meters. Students must be within 50 meters of the latest instructor location. Browser-reported GPS remains spoofable and is a proximity aid, not proof of physical identity.

Expiration finalization runs on subsequent authorized attendance access, using the original roster snapshot. There is no background scheduler in this migration. Finalization clears instructor coordinates, location timestamps and token hashes. Only SHA-256 token hashes are stored; each successful token request replaces the previous token. Failed normal check-in attempts are retained without precise location; failed malformed requests do not enter the database audit. Corrections require an operation UUID and expected revision; notes are optional. Optional recordedAt preserves the offline edit time separately from server commit time and must lie within the meeting timeline. Identical retries are idempotent, conflicting revisions return a conflict without overwriting. Correction and cancellation history reject update and delete. Multiple distinct meetings can share the same date, and closed meetings can be canceled with an audit entry.

Optional push needs `ATTENDANCE_PUSH_ENABLED=true`, `NEXT_PUBLIC_ATTENDANCE_VAPID_PUBLIC_KEY`, `ATTENDANCE_VAPID_PRIVATE_KEY`, and `ATTENDANCE_VAPID_SUBJECT`. Instructor failure notifications are generic, expose no student details or attendance token, and expire after 60 seconds. A database claim groups notices with a five-minute meeting cooldown. The meeting response contains up to 100 recent scoped failures for on-demand review. Only known browser push-service endpoints are accepted. Delivery is best effort and push failure never rolls back attendance changes. There are no student meeting-open notices.

Run `node --test tests/attendance-db.test.mjs` for in-process PostgreSQL integration coverage. It loads the real migration and checks access denial, identity matching, duplicate roster protection, snapshots, proximity/expiry, one open meeting, manual override protection, correction idempotency/conflicts, offline sync and finalization. Real Supabase deployment, Google sign-in, browser push and concurrent network clients still need environment verification.
